═══ 结论 ═══
1. 两刀代码修复在 release 形态下把扫描期掉帧 24.86% → 1.45%（17 倍），
   是真实有效功：57Hz 主线程风暴连 release 也扛不住。
2. debug 形态即使不扫描也 60-77% 掉帧（中位 57ms）——用户日常侧载 debug 包
   的「滚动卡顿」主体是 debug 构建固有开销（JIT+调试运行时+未优化代码生成），
   代码侧不可修。日常使用应侧载 release 签名包。
3. framestats 佐证：慢帧集中在 traversal 派发 26-76ms（debug Compose 遍历），
   measure/layout 子阶段与 GPU（3-6ms）均无罪。

═══ 坑位账（本轮新增）═══
- adb install 输出接 `| tail` 会吃掉失败退出码：增量安装异常后静默无操作
  （08:47 那次「装了」实际 lastUpdateTime 未变）——install 必须裸跑看 Success。
- EMUI install 走 "Incremental not allowed" 异常后回退 Streamed Install 属正常，
  以末行 Success 为准。
- 手机侧验尸法：onScanResult 日志的 TID==PID → 旧码（主线程回调）；
  TID!=PID → 修复版（ble-scan-callbacks 工作线程）。比 gfxinfo 数字更硬。
- gfxinfo 单轮测量受热态影响方差大（debug 49%↔77%），归因结论必须建立在
  重复测量 + 对照矩阵上。
