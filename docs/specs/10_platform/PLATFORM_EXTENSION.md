## 1. 产品能力的平台无关性盘点

按跨平台 SOP 原则二，先从六域中分离「产品能力」与「平台绑定项」：

| 域 | 产品能力（平台无关，Base 原型已定义） | 平台绑定项（各平台差异层） |
|---|---|---|
| 设备发现 | 扫描会话/节流合并/筛选/广播查看/显示名 fallback（F001–F005） | 扫描 API 形态（连续扫描 vs 选择器）、权限模型 |
| GATT 调试 | 连接/服务树/读写/监听/日志/重连/多会话（F006–F013） | GATT API 差异（基本一致：connect/discover/read/write/notify） |
| 广播发射 | 参数定义/31B 预算核算/状态机（F014–F016） | **外围能力有无**（平台分化最大点） |
| Profile 配网 | 向导/扫码/分帧明文写/状态跟踪/错误恢复/诊断（F018–F022、F024） | 扫码实现、权限与 BLE API 差异；V1 简化各平台均不得发起系统配对 |
| OTA | 12 态事务/校验/传输/版本回读（F025，BLOCKED） | 纯 GATT 事务 + 文件选择器，跟随 GATT 能力 |
| 系统信息 | 版本投影/分享（F027–F029） | 分享机制（社交卡片/系统分享/URL/文件） |

结论：**核心产品逻辑（S1–S6 旅程、状态机、数据模型）全部平台无关**；平台分化集中在 4 个绑定项，其中「广播发射外围能力」是唯一可能整域缺失的点（Web）。

## 2. 四平台分析（SOP §8 结构：优势 / 限制 / 可能增强）

### 2.1 微信小程序（现有主平台 · 基准已就绪）

- **优势**：微信生态分享直达（F029 现状）、零安装快速触达、扫码/授权引导链路成熟（F002/F020 现状）。
- **限制**：后台即挂起（扫描/连接仅前台，现状 onUnload 停扫即为此设计）；peripheral 广播能力有限（wx.createBLEPeripheralServer，功率三档映射，PRD F014 现状）；包体与类目审核。
- **宿主系统维度（2026-09-03 用户走查补充）**：微信小程序区分运行宿主——安卓 / iOS 真机、开发者工具等，旧代码已有此维度（`apps/uniapp/pages/broadcast/index.vue` 的 `isWeixinDevTools()` = `wx.getDeviceInfo().platform==='devtools'` 区分开发者工具：外围广播不可用需真机调试；`pages/about/index.vue` 展示宿主 `osName`/机型）。宿主事实：安卓 / iOS 真机走同一 wx BLE API 路径，行为一致；开发者工具外围服务不可用；PC 端微信 BLE 支持旧代码未覆盖【未知，未验证】。原型呈现：`prototype/platform/wechat/high-fi/assets/wxhost.js` 宿主切换覆写层（P009 切换入口 / P008 宿主徽标与 devtools 启动拦截）。
- **可能增强**：无新增（保持基准；SOP 原则——平台不改变产品）。
- **扩展成本**：零（v1 直接实现，其余平台向它对齐）。

### 2.2 App · uni-app（Android 现有部分能力 / iOS 现状 future）

- **优势**：系统能力完整——Android 原生插件广播已有（LysBlePeripheral，F015 现状）；可后台受限保连；系统文件选择（OTA 选包/日志导出更自然）；系统级分享。
- **限制**：iOS 端 BLE 需原生开发（现状 NOT_RELEASED）；后台连接受 Doze/电池优化约束；商店分发成本。
- **可能增强**（SOP §8「可能增强」要求项，均**建议候选**，非本轮决策）：日志导出为文件（复用 F011 导出能力+系统分享）；后台保连通知（长时 notify 监听场景）；Android 蓝牙快捷设置直达（现状已有 Intent 引导，PRD F015）。
- **扩展成本**：低——uni BLE API 与 wx 同构（REVERSE §「平台 API 收敛于少数文件」），扫描/GATT/配网三域 UI 可直接复用，主要工作为 iOS 端规划（若做）。

### 2.3 Web（现状 UNSUPPORTED → 本轮进入评估）

- **优势**：零安装、URL 直达（U4 教学场景价值）；桌面浏览器大屏适合日志阅读。
- **限制（硬约束，公开技术事实）**：
  - **无自由扫描**：Web Bluetooth 仅有 `requestDevice` 选择器模式（过滤条件→系统弹窗选择单台），产品 F001「连续扫描+列表筛选」整域不可实现（watchAdvertisements 为实验性 API【待验证】）。
  - **无广播发射**：LE Advertising 无稳定 API【实验性，2026 状态待验证】——F014–F016 广播域整域缺失。
  - GATT 调试域**可用**：连接后 read/write/startNotifications 完整（F006–F013 子集可迁移）。
  - 仅安全上下文（HTTPS）；浏览器兼容分化（Chrome/Edge 支持完整，Firefox 不支持，Safari 桌面有限支持【待验证】，iOS 全系浏览器不支持）。
- **可能增强**：URL 参数预填配网信息（纯前端，零后端约束内）。
- **扩展成本与定位问题**：S1（扫描发现）与 S4（广播）两条核心旅程断裂，只能承载「已知设备的 GATT 调试器」子集 → 存在平台 D3（见 §6）。

### 2.4 Desktop（全新平台，从未有过）

- **优势**：长时间运行（U1 固件开发者长时 notify 监听/日志采集价值最高）；文件系统（OTA 固件管理、日志落盘导出）；多窗口大屏（多设备并行调试对比）。
- **限制**：跨平台 BLE 无统一 Web API——需原生层（macOS CoreBluetooth / Windows WinRT / Linux BlueZ）或跨平台库（btleplug 系）；Electron 的 Web Bluetooth 支持不完整，通常走原生集成【待验证：技术选型 spike】；分发/签名/自动更新成本。
- **BLE 能力判定**：经原生层，扫描/GATT/广播外围均可为 △～✅（Linux 广播受 BlueZ/内核权限影响【待验证】）——**四平台中唯一可能全域达标的扩展平台**，代价是实现层最厚。
- **扫码（F020）**：配对码通过**扫描二维码**获取（产品统一口径，2026-09-03 用户修正）——桌面端主路径 = 摄像头读取 ControlHub 屏显 `shid://pair` 二维码；无摄像头 / 无法扫码时以**粘贴 / 手输**兜底（内容直接解析，纯前端可解）。原型呈现：`prototype/platform/desktop/high-fi/desktop.js`（扫码 sheet 取景器 + 兜底入口）。
- **操作系统维度（2026-09-03 用户走查追加）**：桌面端区分三宿主 OS——**macOS（CoreBluetooth）/ Windows（WinRT）/ Linux（BlueZ）**，与生态矩阵（11_ecosystem §2 平台编号 WIN/MAC/LINUX）口径一致；Linux 广播外围受 BlueZ / 内核权限影响【待验证】。窗口 chrome 随系统三形态（mac 交通灯左侧 / win 右侧─▢✕ / linux 仅✕，系统还原层豁免圈外色值）。原型呈现：`desktop.js` OSES 注册表（P009 操作系统切换入口 / P008 平台徽标 `Desktop · {OS}` 与原生层提示 / 评审栏生态能力矩阵卡随 OS 随动）。D2 spike 未启动，能力细节不预判。
- **可能增强**（建议候选）：日志文件流式导出；OTA 固件库本地管理；多设备并排工作台。

## 4. 平台差异设计（SOP §9：核心功能一致，表现方式不同）

## 7. 平台扩展检查表（SOP §11，供各平台原型验收）

每个平台原型完成后逐项三查：

1. **功能**：对照 [FEATURE_MAP.md](../02_product/FEATURE_MAP.md) 29 项——纳入域全部保留核心能力；能力缺失域按 §3 矩阵「明确不支持+指引发小程序/App」（延续 P008 Web 分支现状模式）。
2. **限制**：符合平台规则（权限引导/生命周期守则/商店或浏览器约束），无静默降级。
3. **增强**：平台优势项（§2 各平台「可能增强」）逐条决策做/不做，并记录于该平台原型文档。

平台原型引用要求（SOP §10）：每平台原型必须引用——① 基准原型（prototype/v1-new）② 本文档平台能力/限制条目 ③ 对应差异设计行。
