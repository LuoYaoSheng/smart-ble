# UniApp 参考产品与开源交付设计

日期：2026-08-31

状态：已确认

## 决策

Smart BLE 暂停并行统一其他客户端，先把 UniApp 完成为第一个可发布、可验证的参考产品。第一阶段正式目标是 UniApp Android App 和微信小程序；UniApp iOS App 随后按同一契约补齐，H5 只提供页面、文档和明确的 BLE 降级体验。

当前微信小程序代码作为事实基线，但产品定义迁移到 `docs/product-contract/`。产品契约优先于旧审计、旧原型和平台 README。所有功能、页面、流程、测试和硬件使用稳定 ID，后续客户端只能实现契约，不能各自重新定义产品。

## 交付架构

```text
产品契约
├── 功能目录 / 用户流程 / 页面契约
├── Android / 微信 / iOS / H5 适配矩阵
├── ESP32 协议、故障注入和测试矩阵
├── 发布门禁
├── HTML 可交互原型规范
└── 公开落地页规范
        ↓
HTML 原型（微信/Android/iOS/H5 模式）
        ↓
UniApp 实现 + ESP32 参考固件
        ↓
自动化 → Android 真机 → 微信真机
        ↓
落地页只发布已证明能力
```

HTML 原型不是统一外观，而是统一任务和状态。平台选择器切换导航、权限、字段和能力限制；功能编号、业务对象和成功标准保持不变。

ESP32 LightBLE 从示例升级为标准开源测试夹具，覆盖稳定广播名、主服务、权限组合服务、Notify、LED 指令、OTA 和可重复故障注入。Android 和微信使用同一固件完成各自允许的 Must 流程。

公开落地页继续使用现有 VitePress，分为产品入口与开发者规范中心。页面明确当前主版本、平台状态、ESP32 快速开始、交互原型、测试证据和贡献方式，不暴露内部审计杂音，也不宣称未经真机证明的能力。

## 验收方向

先完成产品契约和原型，再补 ESP32 自动测试和故障注入；随后修复 UniApp 契约缺口，依次完成 Android 真机和微信真机。只有通过发布门禁后，能力才进入落地页正式声明。
