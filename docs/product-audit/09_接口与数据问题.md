# 09 · 接口与数据问题

> 汇总微信 API 调用规范、数据结构、存储与状态机问题。判定视角：会不会产生**数据错乱、静默失败或未来回归**。

---

## 1. API 调用规范（fail 回调缺失清单）

微信异步 API 的 `fail` 回调缺失 = 失败静默。全应用扫描结果：

| 编号 | 调用点 | fail 现状 | 影响 | 严重度 |
|---|---|---|---|---|
| A01 | `scanControlHubQr` 的 `uni.scanCode`（composable:127） | `fail: () => {}` 空体 | 相机权限拒绝完全无反馈（=08/FC-02） | P2 |
| A02 | `chooseMessageFile`（P006 OTA） | 仅 `console.error` | 用户选文件失败无感知 | P3 |
| A03 | `stopAdvertising`（P007） | 无 fail 处理 | 停止失败状态不回滚 | P4 |
| A04 | 广播页 `openBluetoothAdapter` / `startAdvertising` | 有 fail（含 10008 降级） | ✅ 处理最完整的一处 | — |

**对照正面基线**：runtime 层（connect/scan/读写）全部经 `normalizeBleError` 归一化，fail 覆盖率 100%。缺失集中在**页面层直调**的 API——再次印证「绕过 runtime 的调用是质量洼地」（与 08 §3 同根因）。

## 2. 数据结构问题

| 编号 | 问题 | 证据 | 影响 | 严重度 |
|---|---|---|---|---|
| S01 | **设备编号双轨**：BLE 广播名用 `SHID-` 前缀（WEAK 识别），配网元数据 device_id 匹配 `^HID-[A-Z0-9]{8}$`，两套编号并存且页面各显示各的 | `services/smart-hid/profile.js` vs `core/protocols/hid-provisioning-protocol.ts` DEVICE_ID_PATTERN；P002-I05、P003-I02 | 用户在同一页面看到两种「设备 ID」，无法建立单一心智模型 | P3 |
| S02 | `scannedDevices[].connected` 字段设计了但永不写入 | P001-I07 | 连接态禁用 UI 不可达（死状态字段） | P3 |
| S03 | P006 遗留 `options.device` JSON 字符串分支 | P006-I04 | 旧格式兼容代码与新对象传参并存，双路径维护成本 | P4 |
| S04 | `workflow.smartHidRecoveryAction` 恢复动作映射零消费方，实际生效的是 composable 的 `recoveryFor` | P002-I03 | 两套词汇表（重试连接/重试 Wi-Fi vs recovery 枚举）无同步机制，改一处漏一处 | P3 |
| S05 | 已连接计数口径不含配网中设备 | P001-I04（`store/ble.js:40` connectedDevicesList） | 计数与列表视觉不一致 | P2 |

## 4. 状态机问题

| 编号 | 问题 | 证据 | 影响 | 严重度 |
|---|---|---|---|---|
| M01 | `adapterReady` 不区分 central/peripheral 模式 | runtime `index.js:266-276`；广播页直调开 peripheral | 双模冲突时标志失真（=08 §3 P1 风险的代码层根因） | P1（待真机定级） |
| M02 | 固件状态机 error 态缺时间戳 | P004-I04（lastError 无 timestamp） | 无法判断错误新旧 | P4 |
| M03 | scan-session 状态机完成回调永不 reject | ✅ 正向基线（设计正确：完成不是错误） | — | — |
| M04 | 配网三阶段向导无「配置中连接断开」的转移边 | P002-I02 | 状态机缺一条边：provisioning × disconnected | P2 |

## 5. 结论

1. **正向基线扎实**：runtime 层的错误归一化、scan-session 状态机、storage 版本号、敏感数据内存化四处设计高于同类小程序平均水平。
2. **问题聚集度高**：A01-A03（页面层直调）、S01/S04（双轨）、M01/M04（状态机缺边）——绕过统一层的代码是数据与状态问题的重灾区。修复策略应是**收口而非打补丁**：把广播页适配器调用收进 runtime、把恢复词汇表合并为单一来源。
3. 最值得警惕的是 M01：它同时是 08 §3 P1 风险的根因，若真机复现，修复必须动 runtime（增加 mode 维度与 open 幂等重入），而非在广播页加 try-catch。
