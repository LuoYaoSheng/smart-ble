# 08 · 假完成清单

> 「假完成」定义：**界面上存在可交互元素，给用户「能做到这件事」的预期，但链路终点并不存在该能力**。这是比 bug 更严重的品类——它消耗用户信任。
> 审计方法：对九页全部操作按钮做终点追踪（页面→事件→服务→反馈），终点落空者入册。

---

## 1. 确认的假完成（2 处）

### FC-01 · P003「高级 BLE 调试」按钮 💀

| 项 | 内容 |
|---|---|
| 位置 | `pages/hid-device/detail.vue:103-105` |
| 表面行为 | 详情页功能区的「高级 BLE 调试」入口，用户预期进入该设备的 GATT 调试界面 |
| 实际链路 | `goAdvancedBle = () => { uni.switchTab({ url: '/pages/index/index' }); }` —— 仅切换到首页 Tab，**不携带 deviceId** |
| 为何是假完成 | ① 目标能力（从指定设备进入调试）不存在；② 即使到首页，该 READY 设备已关广播**扫不到**，用户连手动找回的补救路径都不通 |
| 用户影响 | 点击后「看起来像跳错了页」，无法理解发生了什么 |
| 严重度 | **P2** |
| 修复方向 | 方案 A：真实实现——携带 deviceId 跳 P006 通用详情（连接若在则直接可用）；方案 B：删除按钮。禁止维持现状 |

### FC-02 · P002 扫码相机权限死路径 💀

| 项 | 内容 |
|---|---|
| 位置 | `composables/use-smart-hid-provisioning.js:127`（`scanControlHubQr` 的 `fail: () => {}`） |
| 表面行为 | 向导内「扫码」按钮，用户预期弹出相机扫码 |
| 实际链路 | 相机权限被拒时 `uni.scanCode` 走 fail 回调，回调体为空——**无 toast、无弹窗、无状态变化**，界面完全静止 |
| 缓解因素 | 该按钮当前是死代码路径（P002 页面的真实扫码入口走 P001 Smart HID 卡片链路），**尚无真实用户流量**；但一旦入口接通，立即成为真·假完成 |
| 用户影响 | 权限被拒的用户会反复点击，认定功能坏了 |
| 严重度 | **P2（潜伏）** |
| 修复方向 | fail 回调中区分 `errMsg`：权限拒绝 → 引导弹窗（跳设置说明）；取消 → 静默返回 |

## 2. 边缘案例（诚实降级，不计入假完成）

以下路径**表面受限但明确告知了用户**，属于微信平台限制内的诚实设计，与假完成划清界限：

| 案例 | 处理方式 | 为何不算假完成 |
|---|---|---|
| P008 官网/反馈链接 | 复制到剪贴板 + toast「网址已复制」 | 明示复制而非跳转 |
| P008 分享应用 | `showShareMenu` + toast「请点击右上角分享」 | 明示平台限制与正确操作 |
| P008 跳转其他小程序失败 | fail → 模态弹窗说明原因 | 有兜底反馈 |
| P003 重新配网（READY 设备） | 弹窗如实告知「设备已关广播，需等待进入恢复模式」 | 不伪装成功，如实告知长路径（FIX-04①） |
| P006「导出日志」 | 实为复制剪贴板 | 有 toast 反馈；命名与行为有落差（07-D16 记录为 P4 打磨项，非欺骗） |

## 3. 系统性风险 · 适配器双模冲突（P1，待真机验证）

严格说这不是「假完成」而是**潜在的全局性功能破坏**，因其严重度高于上述两处，在此单列：

| 项 | 内容 |
|---|---|
| 位置 | `pages/broadcast/index.vue:214` / `:554`（直调 `wx.openBluetoothAdapter({mode:'peripheral'})`）；`services/ble-runtime/index.js:266-276`（`adapterReady` 标志）；全仓库（无 `closeBluetoothAdapter`） |
| 风险机制 | 广播页绕过 runtime 单属主层直接以 peripheral 模式开适配器；runtime 的 `adapterReady` 是 central 语义的标志，对模式变化无感知。用户「开广播 → 切 Tab 扫描」时，runtime 认为 `adapterReady=true` 跳过重新 open，central 扫描可能失败，且报错（10001/10008 类）指向错误方向 |
| 触发条件 | 双角色用户 + Tab 顺序切换（先广播后扫描） |
| 当前不确定性 | 微信基础库可能内部兼容双模式共存；**必须真机验证后才能定级**：若复现 → P1 实锤；若不复现 → 降级为 P3 架构债（仍建议统一收口到 runtime） |
| 影响面 | 一旦复现，影响 P001/P002 全部扫描与连接功能，且用户无自愈手段（无 close 出口） |

## 4. 结论

| 品类 | 数量 | 编号 |
|---|---|---|
| 确认假完成 | 2 | FC-01、FC-02 |
| 系统性风险（待验证） | 1 | 适配器双模冲突 |
| 诚实降级（非问题） | 5 | 见 §2 |

**总体判断**：假完成密度低（9 页 40+ 操作中仅 2 处），且两处均不在主链路上——这印证了上轮 12 项修复的诚意。真正需要在发版前解决的，是把 P1 双模冲突验证清楚（12_修复路线图 Phase 0）。
